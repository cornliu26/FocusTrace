# FocusTrace 产品纲领

这份文档是 FocusTrace 的产品决策基线。功能数量不是目标；让真实工作中的注意力更可见、更容易恢复、并能被逐步改善，才是目标。

## 三个核心问题

### 1. 看清：忙碌不等于推进

用户需要知道自己是在合理地使用多个工具，还是在工作流之间反复跳转。

FocusTrace 应当区分应用切换、工作流切换和经过用户确认的偏离，用本地时间轴还原事实，不根据一次切屏武断判断注意力。

成功信号：

- 用户能解释一段高频切换发生了什么；
- 合理的工具切换不会被当成分心；
- 数据不足或归因不可靠时，产品明确说不能判断。

### 2. 不丢：切走之后能够回来

Agent 等待、新消息和口头需求会自然打断工作。产品不应要求用户拒绝一切切换，而应降低保存上下文和返回原任务的成本。

FocusTrace 应当让新需求先被收下，让工作流保存稳定上下文，让用户明确开始处理，并在离开后保留可恢复的下一步。

成功信号：

- 收下需求不会切换或绑定工作流；
- 用户知道什么必须在什么时候处理；
- 开始、挂起、返回和完成都有明确出口；
- 完成一个需求不会误结束整个工作流。

### 3. 改善：一次改变一个可验证变量

用户需要的不是泛泛的“少分心”，而是适合自己的训练长度、时段和工作方式。

FocusTrace 应先建立个人基线，再根据足够的数据提出一项可解释调整，由用户确认并用后续训练验证。产品记录行为，不诊断或治疗 ADHD。

成功信号：

- 建议引用可读的本地聚合证据；
- 一次最多改变一个训练变量；
- 数据质量不足时不生成行为结论；
- 用户可以拒绝或回退计划。

## 每个功能必须通过的三道门

### 问题门：是否解决真实问题

功能提案必须写清：

- 主要服务上面的哪一个核心问题；
- 用户现在在哪里受阻；
- 完成后可观察到什么不同；
- 用什么行为指标或可用性证据判断有效。

“增加一个页面”“显示更多数据”“支持一个字段”不是问题陈述。

### 边界门：是否知道自己不解决什么

功能提案必须写清：

- 不处理的相邻问题；
- 需要采集的数据以及为什么必要；
- 哪些信息明确不采集；
- 哪些决定必须由用户确认；
- 失败、数据不足或权限缺失时如何降级。

默认边界：

- 不诊断或治疗 ADHD；
- 不采集窗口标题、URL、输入内容、聊天对象或手机行为；
- 不自动封禁应用、修改系统通知或替用户决定优先级；
- 不演变成团队项目管理、日历排期或员工监控工具。

### 闭环门：流程是否能够自己完成

一个流程至少要有：

1. 触发：用户为什么会进入；
2. 行动：当前唯一的主要下一步；
3. 反馈：系统如何说明发生了什么；
4. 恢复：被打断、失败或退出后如何继续；
5. 完成：怎样明确结束；
6. 验证：怎样判断解决了原问题。

只有入口或只有展示，不算完成的产品流程。

## 需求与工作流的关系

- 需求描述需要交付的结果，具有截止时间、重要程度和顺序。
- 工作流保存持续工作的上下文，可以包含多个需求。
- 收下需求时不要求选择工作流，也不改变当前上下文。
- 整理需求时分别决定截止时间、重要程度和工作流归属，三者不能混为一个“优先级”。
- 只有跨越多次工作时段、包含多个步骤或需要独立 Space/工具上下文时，才建议创建新工作流。
- “开始处理”是唯一可以激活需求上下文的动作；系统不得因为捕获或整理需求自动切换。

## 迭代方式

- 小步：一次只引入一个能够闭环的行为变化。
- 可证：先定义验收证据，再实现。
- 不劣化：保留既有功能、UX、性能、数据兼容和部署回归测试。
- 可回退：数据迁移向后兼容，产品规则和训练计划保留版本。
- 诚实：区分事实、推断和未知，不用更多图表掩盖数据质量问题。
