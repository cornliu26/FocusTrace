# 决策：Codex 复盘先交付问题，再交付今天的动作

- 状态：已采纳
- 日期：2026-07-25
- 负责人：FocusTrace
- 主要产品支柱：改善

## 问题

当前 Codex 写回要求同时提供标题、解释、两条证据、建议和下次检查。这个结构会诱导 Codex 用不同说法重复同一组数字，并把隐私说明、阶段解锁进度等背景放在真正结论之前。用户读完仍无法迅速回答两个问题：今天最值得处理的阻塞是什么，以及接下来具体做什么。

## 预期结果与证据

打开复盘后，用户首先看到唯一的“当前问题”，随后看到唯一的“今天怎么做”和可验证的验收标准。新协议最多使用两条不重复的聚合证据，不再要求解释段落；完整写回正文限制在 360 个字符内。回归测试验证输出结构、数据不可靠时的拒绝判断、信息预算和旧版写回兼容。

## 边界

- 本次明确不解决：让 Codex 代替用户修改训练计划，生成通用效率文章，或用日志诊断 ADHD。
- 新增数据及用途：不新增数据；继续只使用现有匿名聚合报告。
- 明确不采集：原始活动片段、Bundle ID、窗口标题、URL、输入内容和返回点文字。
- 必须由用户确认的决定：任何训练计划、允许应用或偏好修改仍须由用户确认。
- 数据不足、失败或权限缺失时的降级：只指出一个数据质量阻塞和一个修复动作，并明确写出“当前不能据此判断注意力”。

## 完整流程

1. 触发：每日定时任务生成聚合报告，或用户刷新 Codex 结果。
2. 唯一主要行动：Codex 从可靠性、上一项建议验证和当天建议中选择一个最重要问题，并给出一个当天可执行动作。
3. 反馈：界面用“当前问题—依据—今天怎么做—验收”顺序展示，不显示重复解释。
4. 中断后的恢复：写回未完成时保持“等待 Codex”；旧版写回仍可展示，但只取其标题作为问题，隐藏冗余解释。
5. 完成或退出：校验通过后原子写入当日报告；失败时不展示未校验内容。
6. 验证：下一工作日按一个明确指标判断动作是否有效，或继续处理同一个阻塞。

## 技术与回归

- 业务规则位置：`CodexReviewArtifact`、`CodexWorkspaceContract` 和 `install-codex-review.py`。
- 新增单元测试：写回 v2 的状态、信息预算、单条证据和数据质量拒绝规则。
- 保护的既有回归测试：聚合数据隐私边界、报告与写回 ID/日期匹配、旧版 v1 写回解码。
- 性能工作负载与预算：无新增持续计算；展示只读取已校验短文本。
- 数据迁移与回退：读取端继续兼容 v1；新生成任务只安装 v2。回退代码不会破坏已有 v1 文件。

## 发布切片

一次交付新的 v2 写回协议、严格校验、两段式界面和已连接工作区的指令刷新。它可以独立验证和回退，不改变采集、训练计划或用户数据。
