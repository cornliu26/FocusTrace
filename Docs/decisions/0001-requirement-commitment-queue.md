# 决策：让收下的小需求在该处理的时候重新出现

- 状态：已采纳
- 日期：2026-07-25
- 负责人：FocusTrace
- 主要产品支柱：不丢

## 问题

当前需求箱可以避免口头需求立即打断工作，但“今天 / 本周 / 以后”同时承担了截止时间和优先级的含义。用户无法设置真正的截止日期，也无法表达“重要但不紧急”。需求离开收件箱以后，没有可靠的到期浮现路径；每个需求又容易被引导成一个新工作流。

## 预期结果与证据

用户可以分别决定：

- 什么时候必须完成；
- 在同样紧迫的事情中有多重要；
- 应当在哪个已有工作流中执行，或暂时不指定。

逾期和今天到期的需求会优先出现在需求队列和菜单栏，并在工作时段内只提醒一次。明确点击“开始处理”后才允许进入或绑定工作流。

验收证据：

- 截止日期、重要程度和工作流归属可以独立修改；
- 排序始终是逾期、今天、未来、无日期，同一区间再按重要程度；
- 捕获和整理均不会切换工作流；
- 到期提醒不会重复，完成或归档后不再提醒；
- 没有归属的小需求可以由用户明确选择在当前工作流处理，不自动新建工作流。

## 边界

- 本次明确不解决：时间段排程、工时估算、依赖关系、团队协作、日历同步和自动优先级。
- 新增数据及用途：重要程度、到期提醒发送时间；只用于本地排序和防重复提醒。
- 明确不采集：通知内容、聊天内容、日历内容、需求来源之外的上下文；系统到期通知不显示需求标题。
- 必须由用户确认的决定：截止日期、重要程度、工作流归属和开始处理。
- 数据不足、失败或权限缺失时的降级：系统通知不可用时，逾期和今日数量仍在菜单栏与需求队列中显示。

旧版“今天 / 本周 / 以后”没有保存作出安排的日期，不能可靠推导真实截止日。迁移后保留旧字段并标记为待确认，不擅自制造日期。

## 完整流程

1. 触发：收到口头、消息或会议中的小需求。
2. 唯一主要行动：先用一句话收进需求箱，当前工作流不变。
3. 反馈：需求显示为待整理；用户分别设置截止日期、重要程度和工作流。
4. 中断后的恢复：到期或逾期需求在菜单栏和队列顶部重新出现，工作时段内最多提醒一次。
5. 完成或退出：明确点击开始处理、完成，或归档为不做；完成需求不结束工作流。
6. 验证：需求按紧迫性和重要程度稳定排序，提醒不会重复，状态变化立即从对应队列移除。

## 技术与回归

- 业务规则位置：`FocusTraceCore/RequirementEngine.swift`。
- 新增单元测试：队列分区、排序、提醒去重、旧字段迁移。
- 保护的既有回归测试：需求捕获不切换工作流、Space 归因、菜单栏主行动和持久化兼容。
- 性能工作负载与预算：1,000 个需求完成分区与排序低于 100 毫秒。
- 数据迁移与回退：新增字段可选解码；旧 `priorityRaw` 保留，新版本不再把它当作优先级。

本次只交付“独立整理字段 + 紧迫性队列 + 一次到期浮现 + 明确开始”的闭环。不加入自然语言自动识别日期、日历同步或智能排程。
