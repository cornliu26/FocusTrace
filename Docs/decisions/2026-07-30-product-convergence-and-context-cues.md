# 决策：停止堆功能，将 Space 从目标降为上下文线索

- 状态：产品观察已确认；交互改造待单独验证
- 日期：2026-07-30
- 负责人：FocusTrace
- 主要产品支柱：不丢 / 改善

## 问题

FocusTrace 已经能够记录应用与工作流切换、保存返回点、承接需求、训练注意力并用纵向实验验证建议。继续增加页面、提醒、分数或工作流状态，开始让用户花更多注意力维护工具本身。

其中最明显的摩擦是桌面绑定：语义工作流被要求提前映射到 macOS Space。Space 能帮助系统归因，却不能回答用户此刻真正承诺推进什么、离开前留下了什么状态、回来后第一步是什么。把绑定当作工作成立的前提，会把系统的识别成本转移给用户。

## 预期结果与证据

当前阶段不新增功能模块，先用 10–15 个真实工作日验证现有闭环。只有观察到明确结果缺口，才继续开发。

验证期关注：

- 用户每天维护 FocusTrace 的主动操作时间是否低于 2 分钟；
- 被中断工作留下返回点后，是否更容易恢复；
- 冲动工作流切换是否下降，而不是机械压低所有应用切换；
- 每日分析是否实际改变下一工作日的一项行为；
- 数据准确但行为没有改善时，能否诚实停止功能扩张。

未来若改造日常入口，Space 只能成为经过用户确认的可选上下文线索，不能继续作为语义工作流成立的前提。当前已发布版本仍保留状态栏绑定，以维持既有自动归因和数据兼容；本文不把候选方案描述成已交付功能。

## 边界

- 本次明确不解决：不在文档更新中重写工作流状态机或迁移现有绑定；
- 新增数据及用途：无；
- 明确不采集：继续不读取窗口标题、URL、输入内容、聊天对象、手机或 Agent 内容；
- 必须由用户确认的决定：未来是否让某个 Space 成为自动识别线索；
- 数据不足、失败或权限缺失时的降级：保持工作流未知，不从应用或标题猜测。

## 完整流程

1. 触发：产品功能已覆盖看清、不丢和改善，但用户仍感到绑定负担；
2. 唯一主要行动：冻结功能扩张，按现有版本完成真实使用验证；
3. 反馈：每周只检查维护负担、恢复闭环、冲动切换和建议执行；
4. 中断后的恢复：验证期允许继续使用现有绑定和返回点，不要求迁移数据；
5. 完成或退出：10–15 个工作日后得出“有效、干预无效或工具负担过重”之一；
6. 验证：只有结果证明绑定仍是主要阻塞时，才进入“工作段为主、Space 为可选线索”的独立改造。
