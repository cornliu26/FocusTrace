# 决策：让需求只做处理决定，并让工作流身份保持清晰

- 状态：已采纳
- 日期：2026-07-27
- 负责人：FocusTrace
- 主要产品支柱：不丢

## 问题

需求卡片同时暴露整理、调整、开始处理、在当前工作流处理、完成、转成工作流和归档，用户需要先理解内部状态机，才能决定一条口头需求接下来怎么办。另一方面，同名工作流可以重复创建，又没有明确的删除入口，需求归属和桌面绑定因此容易失去辨识度。

## 预期结果与证据

用户面对一条未完成需求时，只需要决定“处理”或“不处理”。点击处理会优先使用需求已归属的工作流，否则归入当前工作流；没有可用上下文时才询问一次工作流。截止日期、重要程度和工作流归属继续保留，但只作为详情调整，不再成为开始处理的前置门槛。

一个工作流可以承接多条需求；完成其中一条需求不会完成或删除工作流，也不会改变同一工作流下的其他需求。新建或重命名工作流时，清理空白、宽度和大小写后的名称必须唯一。删除工作流前明确展示影响，删除后未完成需求回到未指定工作流，桌面绑定解除，历史时间轴和训练记录保留。

验收证据：

- 未完成需求卡片只有“处理 / 不处理”两个显式决策；
- 没有截止日期或重要程度安排的需求也可以被明确开始；
- 两条需求可以归入同一工作流，完成一条不改变另一条和工作流；
- 同名、大小写变体和多余空白变体不能重复创建或重命名；
- 工作流管理中有明确删除入口和影响确认；
- 删除工作流不删除历史活动、区间或训练记录。

## 边界

- 本次明确不解决：子任务、依赖关系、批量操作、团队协作、自动优先级、工时排期和通用项目管理。
- 新增数据及用途：不新增数据字段；只使用现有需求归属、工作流名称和生命周期完成校验与解绑。
- 明确不采集：需求正文之外的聊天内容、窗口标题、URL、输入内容和任何新的行为数据。
- 必须由用户确认的决定：开始处理、不处理、选择目标工作流和删除工作流。
- 数据不足、失败或权限缺失时的降级：没有当前或已归属工作流时停在工作流选择；保存冲突时保留编辑界面并展示错误；删除失败时不改变原数据。

## 完整流程

1. 触发：需求进入需求箱，或用户回到一条尚未完成的需求。
2. 唯一主要行动：点击“处理”；若明确不做则点击“不处理”并确认。
3. 反馈：需求显示正在处理及所属工作流；详情中仍可调整截止日期、重要程度和归属。
4. 中断后的恢复：需求仍留在原工作流下，可从需求箱再次处理；同一工作流中的其他需求不受影响。
5. 完成或退出：点击“完成需求”只结束该需求；删除工作流则解绑未完成需求、释放桌面绑定并保留历史。
6. 验证：需求动作、归属、独立完成、名称冲突和删除影响即时反映在界面与本地存储。

## 技术与回归

- 业务规则位置：`FocusTraceCore/RequirementEngine.swift`、`FocusTraceCore/WorkflowEngine.swift` 和 `ApplicationState.swift`。
- 新增单元测试：无需完整整理即可开始、同工作流多需求独立完成、工作流名称规范化唯一、删除时只解绑相关需求。
- 保护的既有回归测试：捕获需求不切换工作流、截止日期/重要程度/归属独立、图形日历、Space 归因、工作流完成撤销和 1,000 条需求性能预算。
- 性能工作负载与预算：保留 1,000 个需求分区排序低于 100 毫秒；名称冲突检查只扫描本地工作流列表。
- 数据迁移与回退：不自动合并已有同名工作流；只阻止新增冲突，用户可通过明确删除入口清理。回退代码不会破坏现有数据字段。
