# 决策：更新失败后恢复旧版并提供最小 GitHub 反馈闭环

- 状态：已采用
- 日期：2026-07-29
- 负责人：FocusTrace contributors
- 主要产品支柱：改善

## 问题

用户点击更新后，更新助手会在主 App 退出后替换应用。如果安装目录不可写或替换失败，旧版本虽然能够保留，但不会重新打开，失败原因也无法回到界面。用户只能看到 FocusTrace 消失，不知道更新是否完成、怎样恢复或怎样提交可用反馈。与此同时，直接推 tag 的发版流程在发布前缺少真实替换验收，失败 tag 和半成品 Release 的恢复成本较高。

## 预期结果与证据

更新成功时，新版本重新启动并显示完成状态；更新失败时，旧版本重新启动，说明安全、可行动的失败原因，并提供手动下载与 GitHub 问题反馈。每个正式 Release 必须在公开前通过“旧 App → 新 App”替换、回滚、签名、清单和下载资产验收。

验收证据：

- 可写目录中的隔离旧版能被新包替换，版本、构建号和签名正确；
- 不可写目录中的替换失败时旧版保留，并生成不含用户路径和行为数据的结果；
- GitHub 反馈链接只包含版本、macOS、失败阶段和错误代码；
- 发布工作流失败时 Release 保持草稿，重跑可以继续而不是制造第二个版本。

## 边界

- 本次明确不解决：崩溃分析平台、后台遥测、自动上传日志、Developer ID 公证或跨架构分发。
- 新增数据及用途：仅保留一次更新结果，包括结果、阶段、错误代码、目标版本、构建号和时间，用于重启后解释更新结果。
- 明确不采集：活动记录、Bundle ID 轨迹、工作流名称、需求内容、窗口标题、URL、输入内容、用户名和文件路径。
- 必须由用户确认的决定：GitHub Issue 的最终内容和提交动作始终由用户在浏览器中确认。
- 数据不足、失败或权限缺失时的降级：保留并重新打开旧版；提供手动下载入口，不继续静默替换。

## 完整流程

1. 触发：用户在设置中发现新版并点击安装。
2. 唯一主要行动：FocusTrace 先验证下载包和安装目录，再交给更新助手替换。
3. 反馈：成功后显示已更新版本；失败后显示阶段对应的安全错误和手动下载入口。
4. 中断后的恢复：更新助手回滚并重新打开仍可用的旧版；一次性结果在读取后删除。
5. 完成或退出：成功使用新版，或保留旧版并选择稍后重试、手动覆盖或打开 GitHub 反馈表。
6. 验证：隔离更新验收、失败回滚验收、Issue URL 隐私回归和公开 Release 资产复验全部通过。

## 技术与回归

- 业务规则位置：`FocusTraceCore/AppRelease.swift`、`FocusTrace/UpdateManager.swift`、`FocusTraceUpdater/main.swift`。
- 新增单元测试：更新结果往返、错误文案、GitHub URL 字段和隐私边界。
- 保护的既有回归测试：版本排序、清单校验、部署回滚和本地数据保留。
- 性能工作负载与预算：更新验收只在打包和发版运行，不进入常驻采集路径；常驻 CPU/内存预算不变。
- 数据迁移与回退：更新结果是可删除的一次性 JSON；旧版会忽略它，删除文件即可回退。

## 发布切片

一个可独立回退的切片：失败重启与安全结果、失败态 GitHub 反馈入口、真实更新验收脚本，以及草稿—验证—公开的幂等 Release 工作流。不引入服务器或新的行为采集。
